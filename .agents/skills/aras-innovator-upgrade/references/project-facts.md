## 決策

| 日期 | 決策 | 負責人 | 理由 | 影響／後續事項 |
|---|---|---|---|---|
| 2026-07-31 | 升級協調工具採「受控執行」模式。工具管理工作流、相依關係、Runbook、執行前檢查及證據；已核准且可安全重複的 Script 可自動執行，高風險操作須逐步人工確認。 | 需求方 | 在自動化效率、操作責任及稽核能力之間取得平衡。 | 後續需定義高風險操作的判定及核准規則。 |
| 2026-07-31 | 第一版採單人案件模式；待運行穩定後，再評估多人共享案件模式。 | 需求方 | 第一版優先確保穩定性與資料正確性。 | 第一版不要求多人同時編輯、角色分工或即時協作，但資料模型應避免阻礙未來擴充。 |
| 2026-07-31 | 單人案件模式允許同一位操作人員自行確認後執行高風險操作，不強制第二人登入簽核。 | 需求方 | 符合第一版單人操作範圍，同時以明確確認降低誤操作。 | 執行前須呈現影響、必要備份、停止條件及 Rollback 資訊，並保存確認內容與時間；外部核准證據可選擇附加。 |
| 2026-07-31 | 自動執行採安全白名單；未列入白名單、超出核准限制或無法判定的動作，一律進入單人確認關卡。 | 需求方 | 優先保護環境及資料正確性，避免遺漏新型態風險。 | 白名單須綁定動作版本、目標、輸入限制與前置條件，條件改變時不得沿用原核准。 |
| 2026-07-31 | 第一版採三級動作安全判定：安全白名單內自動執行、重要狀態變更須單次確認、必要條件不足時阻擋。 | 需求方 | 防止人工確認被誤用成繞過安全前置條件的機制。 | 系統須分別記錄判定等級、判定依據、確認內容或阻擋原因。 |
| 2026-07-31 | 已發生的執行歷程不得覆寫。 | 需求方 | 保持案件資料正確、可追溯，並能判斷一次性流程是否已執行。 | 後續需定義錯誤紀錄的更正方式，以及草稿轉為執行歷程的時間點。 |
| 2026-07-31 | 執行歷程有誤時新增更正紀錄，不修改或刪除原紀錄。 | 需求方 | 同時保留原始證據與正確的案件目前狀態。 | 更正紀錄須指向原紀錄並保存錯誤原因、正確內容、時間與操作者。 |
| 2026-07-31 | 動作開始前固定執行快照；從該刻起，該次嘗試及其輸入基準不得覆寫。 | 需求方 | 避免執行期間草稿變動導致證據與實際操作不一致。 | 快照包含輸入、參數、工具版本、Checksum 與目標；成功、失敗及中斷均須保留。 |
| 2026-07-31 | 任務本身保持不變；每次實際運行建立獨立的執行嘗試。 | 需求方 | 保留每次運行的真實狀況，避免重跑覆蓋失敗或中斷證據。 | 各執行嘗試須有自己的執行快照、狀態與結果，並依序關聯至同一任務。 |
| 2026-07-31 | 新增執行嘗試前必須證明可安全重試；否則阻擋。 | 需求方 | 避免失敗或中斷後直接重跑造成額外狀態變更。 | 放行條件為已驗證 Idempotency、已完成 Rollback，或已恢復至 Runbook 指定檢查點之一；須保存判定證據。 |
| 2026-07-31 | 客戶 Package 產生流程異常後，由操作人員手動將 DB 還原至最後備份點；工具不自動執行 DB Rollback。 | 需求方 | DB 還原屬高風險操作，保留人工控制。 | 工具須記錄還原結果及證據；是否解除一次性鎖定仍待確認。 |
| 2026-07-31 | 客戶 Package 產生流程在首次 DB 變更前，由協調工具的固定規則建立一次性流程鎖定，不由 AI 自主判定。 | 需求方 | 鎖定屬安全不變條件，必須可預測且一致。 | 鎖定成功後才能進入 DB 變更；鎖定寫入失敗時阻擋操作，AI 無放行或解鎖權限。 |
| 2026-08-01 | 客戶 Package 一次性流程失敗後，只有手動還原至該次執行前 DB 備份點並提交相符證據，固定規則才標記 `RolledBack` 並允許新執行嘗試；成功產生客戶 Package 基準後鎖定永久完成。 | 需求方 | 完整定義一次性鎖定的安全生命週期。 | 備份識別不符或證據不足時不得解鎖；AI無解鎖權。此決策解決先前尚待確認的鎖定解除條件。 |
| 2026-07-31 | 刪除 Package 相關 Table 的 SQL 由工具受控執行。 | 需求方 | 將高風險 DB 變更納入一致的確認、鎖定及證據流程。 | 僅能執行預先核准、版本固定且 Checksum 相符的 SQL Script；AI 不得產生、修改或自由組合 SQL，DB 還原仍由操作人員手動執行。 |
| 2026-07-31 | 同版本 OOTB Table 的導出及客戶 DB 匯入亦由工具受控執行，與刪除 Package 相關 Table 組成同一客戶 Package 產生流程。 | 需求方 | 維持整段 DB 準備流程的資料一致性及證據完整性。 | 每一步各自建立執行快照、檢查點與結果證據；匯入客戶 DB 前須再次單人確認，失敗時停止後續步驟且不自動重跑或還原。 |
| 2026-07-31 | 第一版的 Aras Package 導出由操作人員人工執行；協調工具只負責引導、追蹤及驗證證據。 | 需求方 | 不同來源版本須使用不同 Export 工具，且客戶環境異常可能需要操作人員取消選取異常項目後重新導出。 | 每次操作均建立獨立執行嘗試；記錄 Export 工具版本、輸出位置、失敗結果、取消選取項目及原因，不覆蓋前次紀錄。 |
| 2026-07-31 | Aras Export 有取消選取項目時，每項都須有明確處置，才能將導出任務標記完成並進入 Package 比較。 | 需求方 | 防止未說明的缺漏進入唯一客戶 Package 比較基準。 | 每項記錄名稱、類型、異常原因，並標示為不屬升級客製內容、已另行補充，或風險已獲接受；未處置者使任務維持已阻礙。 |
| 2026-07-31 | 原始 Package 備份在第一版只保存，不進行比較或修復。 | 需求方 | 其用途是保留客戶既有 Package 狀態，供未來追查因刪除原廠項目造成的異常。 | 備份須保留來源識別、時間、工具版本、位置與完整性證據；不得誤作後續跳點比較輸入。 |
| 2026-07-31 | 完成 OOTB Table 匯入及導出排除項目處置後的產出命名為「客戶 Package 基準」，作為所有升級跳點比較的唯一客戶端輸入。 | 需求方 | 避免與只供保存的原始 Package 備份混淆。 | 兩者須分開存放並標示用途；後續跳點不得改用原始 Package 備份或其他任意 Package。 |
| 2026-07-31 | 第一版升級路徑由操作人員依已驗證的 Aras 原廠文件選定；工具負責連續性驗證、任務編排及相依關係，AI 不得自行增刪或變更跳點。 | 需求方 | 精確版本路徑需以原廠證據及人工責任決策為準。 | 任一跳點開始執行後不得直接修改原路徑；需要調整時建立新版路徑並保留舊版歷程。 |
| 2026-07-31 | 各跳點適配 Package 採半自動產生：確定性規則可自動形成候選產出，衝突、缺漏或多解項目須由操作人員裁決後才能成為正式適配 Package。 | 需求方 | 在自動化效率與 Package 正確性之間取得平衡。 | AI 只提供解釋與建議，不能替代裁決；原始標準 Package、候選適配 Package及正式適配 Package須分開保存且不得覆寫。 |
| 2026-07-31 | AML 一般 Item 配對採分層 Key：優先使用正規化 `type + id`；`id` 不穩定時使用事先定義的 ItemType 專屬業務 Key；Key 缺失、重複或多候選時轉人工確認。 | 需求方 | 遵循 AML 共用標準並避免錯誤自動配對。 | AI 不得臨時推測業務 Key；人工確認項目須輸出 AML Path。 |
| 2026-07-31 | ItemType 專屬業務 Key 使用專案內版本化的「比對 Key 規則集」維護。 | 需求方 | 讓配對規則可追溯並在案件間一致使用。 | 規則版本的生效方式及對既有比較結果的影響仍待確認。 |
| 2026-07-31 | 每次 Package 比較固定比對 Key 規則集版本；規則改版後須建立新的執行嘗試，不得改寫既有結果或自動替換已執行跳點的正式適配 Package。 | 需求方 | 保持比較結果及升級輸入可重現。 | 新執行嘗試產生新的候選適配 Package，舊結果及其規則版本永久保留。 |
| 2026-07-31 | 客戶 Package 基準與跳點標準 Package 的同一 AML Item 內容不同時，若無適用的版本化轉換規則，一律視為 Package 衝突並由操作人員裁決。 | 需求方 | 防止工具或 AI 擅自選擇客戶內容、標準內容或合併方式。 | 差異須涵蓋完整 AML 語意樹並輸出 AML Path；裁決結果及理由納入執行歷程。 |
| 2026-07-31 | 人工 Package 衝突裁決不得直接重用於其他案件或其他升級跳點。 | 需求方 | 裁決依賴當前案件、跳點及輸入內容，直接重用可能造成錯誤合併。 | 每筆裁決只對當次輸入快照有效；是否可另行提升為版本化規則仍待確認。 |
| 2026-07-31 | 允許將已驗證具有通用性的人工裁決另行建立為版本化轉換規則，但不得在案件內直接將本次裁決提升為全域規則。 | 需求方 | 防止單一案件的偶發處置未經獨立驗證便影響其他比較。 | 規則須透過獨立建立與核准流程；具體適用範圍仍待確認。 |
| 2026-07-31 | 轉換規則預設作為不綁定跳點的共同準則；僅在其他版本不符合時，針對不符項目建立指定來源版本與目標版本的版本例外規則。 | 需求方 | 團隊已有共同遵守的準則，避免為每個跳點重複維護相同規則。 | 規則集須同時支援共同準則與版本例外；例外只在發現並確認版本差異後建立。 |
| 2026-07-31 | 共同準則與版本例外規則同時符合時，優先採用版本例外規則。 | 需求方 | 版本例外用於修正共同準則在特定來源與目標版本的不適用情況。 | 多條版本例外同時符合時的衝突處理仍待確認。 |
| 2026-07-31 | 同一差異同時符合多條版本例外規則且結果不一致時，立即阻擋該比較項目。 | 需求方 | 避免以建立時間、排序或 AI 判斷任選規則造成錯誤。 | 衝突須保留於比較結果；其他項目能否繼續處理及正式 Package 的阻擋範圍仍待確認。 |
| 2026-07-31 | Package 比較調整改採強制備份後直接覆寫來源與目的 XML，以只留下差異或新增項目；此決策取代先前「原始、候選及正式 Package 均不得覆寫」的要求。 | 需求方 | 調整後的 XML 本身就是供升級使用的異動內容。 | 使用者不得關閉備份；個別 XML 備份失敗時不得覆寫該 XML；覆寫後的兩端共同形成候選產出。 |
