## 一、分享定位與整體主軸

這份分享的核心不是介紹某一個 AI 工具，而是整理一種新的工程工作方式：如何從 Vibe Coding 的快速探索，逐步走向可驗證、可追溯、可治理、可接手的 Agentic Engineering。

Vibe Coding 的價值在於快。工程師可以使用自然語言快速描述需求，讓 AI 產生原型、程式碼或初步解法。這種方式非常適合探索階段，尤其是在需求尚未完全明確、需要快速驗證想法時。

但是，企業級系統的交付標準不只是「程式可以執行」。還需要確認：

- 需求是否明確且符合業務目標？
- 使用的輸入是否正確、完整且可追溯？
- 結果是否能被測試與重現？
- 發生衝突或資料不足時，系統是否會安全停止？
- 其他人或下一個 Agent 是否能理解並接手？

因此，Agentic Engineering 的重點不是讓 Agent 擁有無限的自主權，而是建立一套讓 Agent 能在清楚規格、測試、證據與授權邊界內工作的工程系統。

## Slide 01｜從 Vibe Coding 到可驗證的 Agentic Engineering

### 本頁目的

建立分享主題，說明本次內容會從 AI 輔助開發的速度，延伸到企業工程所需要的驗證與治理。

### 詳細說明

Vibe Coding 通常從一段自然語言對話開始。工程師可能只需要描述：「請幫我做一個比較兩個版本差異的工具」，AI 就能快速產生介面、程式碼與初步結果。

這種體驗讓開發的起點變得非常低，也讓技術探索速度大幅提高。然而，當需求進入真實企業環境，問題會變得更複雜。例如 Aras 升級涉及多個版本、資料來源、客製化內容與 OOTB 標準內容。此時，單純產出一支「能跑的腳本」並不足以支撐正式決策。

本次分享以以下路徑為主線：

> 想法 → 規格 → 垂直切片 → 測試 → 證據 → 可交付成果

### 分享心得

我認為 AI 輔助開發真正的挑戰，不是能不能產生程式，而是能不能讓產出成為團隊可以信任、檢查與接手的工作成果。

### 建議講述時間

約 1.5–2 分鐘。

### 銜接語

「先從 Vibe Coding 的優勢開始，接著說明為什麼它還需要工程流程來補強。」

## Slide 02｜核心關鍵：從「快、可工作」走向 Agentic Engineering

### 本頁目的

對比 Vibe Coding 的價值與限制，建立為什麼需要 Agentic Engineering 的問題意識。

### Vibe Coding 的優勢

#### 1. 快速產生原型

需求剛開始討論時，團隊往往很難只靠文字確認畫面、流程或資料結構是否合理。透過 Vibe Coding，可以迅速得到一個能互動的原型，讓討論從抽象描述變成具體物件。

#### 2. 降低程式撰寫門檻

工程師不必先處理大量樣板程式、語法細節或框架初始化，就能快速進入問題本身。對熟悉業務、但不一定熟悉所有技術細節的人而言，這種方式能提高參與度。

#### 3. 加速早期探索

在架構或解法尚未確定前，快速嘗試多種方向，可以更早發現錯誤假設，降低投入大量時間後才推翻方案的風險。

### Vibe Coding 的斷點

#### 1. 需求與輸入邊界模糊

如果沒有明確定義輸入範圍、資料來源與不處理的情況，AI 會依照上下文自行補足缺口。這些補足可能看似合理，卻不一定符合真實業務規則。

#### 2. 驗證高度依賴記憶

原作者可能知道自己曾經測過哪些情境，但這些測試不一定被記錄，也不一定能由其他人重現。

#### 3. 團隊難以接手

如果重要決策只存在於聊天記錄或作者記憶中，下一個人或下一個 Agent 就難以理解原本的設計意圖。

### 分享心得

「能跑」代表技術上有某種結果；「能交付」則代表結果有清楚的來源、驗證方法、風險處理與接手方式。兩者之間的差距，就是工程流程要補上的地方。

### 建議講述時間

約 3–4 分鐘。

## Slide 03｜Matt Pocock 流程：先對齊，再實作

### 本頁目的

說明 Agent 工程流程的第一個重要習慣：在開始寫程式前，先把不確定性顯性化。

### 詳細說明

很多開發問題並不是程式能力不足，而是需求還沒有被說清楚。當需求模糊時，Agent 只能根據語境猜測，例如：

- 這個功能真正要解決的問題是什麼？
- 哪些資料可以讀取？
- 哪些操作不被允許？
- 哪些情況算成功？
- 缺資料時應該繼續、跳過，還是停止？

先對齊的目的，就是把這些問題移到實作前處理。這包含：

1. 定義目標。
2. 定義非目標與限制。
3. 定義輸入與輸出。
4. 定義驗收條件。
5. 定義例外與停止條件。

### 文件的角色

文件不是為了增加流程負擔，而是作為 Agent 的導航資料。當規格清楚時，Agent 可以更自主；當規格不清楚時，人反而需要花更多時間反覆修正與監控。

### Aras 案例連結

例如「比較 Customer 與 R38」還不夠具體。需要進一步說明比較哪些目錄、使用哪些版本證據、差異如何分類，以及版本不一致時是否停止。

### 分享心得

越早把不確定性說出來，後面需要返工的機率越低。規格不是限制創意，而是讓創意可以被正確實作。

### 建議講述時間

約 2.5–3 分鐘。

## Slide 04｜Aras 升級協調工具背景

### 本頁目的

說明為什麼 Aras 升級適合作為 Agentic Engineering 的實戰案例。

### 詳細說明

Aras Innovator 升級通常不只是單純替換版本。過程可能同時涉及：

- 資料庫內容。
- Package。
- AML。
- Core Tree。
- Customer 客製化內容。
- OOTB 標準版本內容，例如 R38。

客製化內容與新版本標準內容之間，可能存在相同路徑、相同元件或相互影響的差異。如果只用人工逐項比對，很容易遺漏；如果只依賴一次性腳本，也很難在不同案件、不同版本與不同輸入條件下重複使用。

### 什麼是多跳流程

這類升級流程通常包含多個相依節點：

> 輸入與版本證據 → Core Tree 比對 → 差異分類 → 影響評估 → 升級計畫 → 執行或阻擋 → 驗證與證據封存

後一個節點必須依賴前一個節點的結果。如果版本證據不足，後面的比較就不應繼續；如果差異涉及高風險衝突，就應該進入人工判斷。

### 為什麼需要阻擋報告

在企業場景中，安全地停止比自動產生一個不可靠的答案更有價值。阻擋報告應清楚描述：

- 為什麼停止。
- 缺少哪些資料。
- 哪些風險尚未判斷。
- 需要補充什麼資料才能繼續。

### 建議講述時間

約 3–4 分鐘。

## Slide 05｜從對話到規格：專案演進路徑

### 本頁目的

呈現如何將一開始的自然語言討論，逐步轉化為可管理、可執行的工程成果。

### 四個階段

#### 1. 規則與對齊

建立專案工作規則，統一 Domain 專屬術語、資料邊界、權限限制與安全要求。

這一步可以避免不同人或不同 Agent 對同一個詞產生不同理解。例如「版本」、「Customer」、「OOTB」、「Core Tree」都應有一致定義。

#### 2. 需求契約化

把需求寫成 PRD 與輸入／輸出契約，清楚定義工作範圍、資料來源、輸出格式、完成條件與停止條件。

#### 3. 任務與 Skills

將大目標拆解成 Issue、Spec 與可重複使用的 Agent Skills。每個小任務都應有清楚的輸入、輸出與驗證方式。

#### 4. 可追蹤交付

透過 Git、Worktree、自動化測試與證據保存，讓每一次變更都能被檢查、回溯與接手。

### 分享心得

這四個階段的價值，在於把「一次對話」轉成「可以累積的工程資產」。未來即使換人或換 Agent，也不必重新從零開始理解。

### 建議講述時間

約 3 分鐘。

## Slide 06｜Skills：將判斷轉化為可重複流程

### 本頁目的

說明 Skills 如何把專業判斷與作業規則轉換成可重複執行的流程。

### 詳細說明

#### 1. 管理升級個案狀態

記錄目前案件處於哪個階段、使用哪些版本，以及之前已完成哪些工作。這讓流程不必依賴單一聊天視窗的上下文。

#### 2. 驗證 Core Tree 輸入契約

在真正比較前，先檢查目錄結構、必要檔案、版本資訊與前置條件是否符合要求。

#### 3. 進行差異比對與分類

將 Customer 與 OOTB 內容進行 Logical Path Mapping，並依規則將差異分類，避免每次都用人工直覺判斷。

#### 4. 封裝升級交付包

產出人工複核報告、Evidence 清單與相關執行紀錄，讓結果不只是一個終端畫面，而是一份可審查的交付包。

### Skill 的設計要素

一個好的 Skill 應包含：

- 什麼情況會被觸發。
- 需要哪些輸入。
- 執行順序與檢查點。
- 成功與阻擋時的輸出。
- 哪些情況必須停止並請示。

### 分享心得

Skills 的真正價值，不只是自動化，而是將團隊的判斷方式保存下來，讓品質可以被重複，而不是只依靠資深同仁的經驗。

### 建議講述時間

約 3 分鐘。

## Slide 07｜Core Tree 比對：垂直切片實作

### 本頁目的

以 Core Tree 比對示範一個「窄而完整」的垂直切片。

### 三方真實輸入

本實作不是使用抽象的測試資料，而是載入三方基準：

- Customer Core Tree。
- OOTB 12SP9。
- OOTB R38。

這三方資料可以讓流程同時觀察客製化內容、原始版本與目標版本之間的關係。

### Logical Path Mapping

不同版本或不同來源的檔案結構可能不完全相同，因此不能只靠檔名或位置直接比對。Logical Path Mapping 的作用，是將 Client 與 Server 的檔案、路徑與邏輯元件對齊，建立可比較的基準。

### A／B／C 差異分類

差異分類的價值在於，讓後續處理有一致的判斷依據。不同類型的差異可能代表：

- 可以直接納入升級計畫的低風險差異。
- 需要進一步分析的相依差異。
- 必須交由人工確認的高風險衝突。

實際分類規則應由專案規格明確定義，不能讓 Agent 每次自行猜測。

### Immutable Input 與證據

比對時使用的輸入應被固定並留下識別資訊，例如版本、檔案清單、Checksum 或其他不可變證據。這樣後續若有人詢問「這個結果是用哪些資料產生的」，可以回到原始輸入。

### 為何這是垂直切片

它不是只做一段比對演算法，而是從真實輸入驗證開始，走過映射、分類與證據輸出，形成一條端到端的可驗證路徑。

### 建議講述時間

約 3–4 分鐘。

## Slide 08｜可評估性：Logs、Traces & Metrics

### 本頁目的

回答「如何知道 AI 做了對的事情」，並說明 Agent 執行需要被觀測與評估。

### Logs：發生了什麼

Logs 應記錄關鍵事件，例如：

- 使用了哪個案件與版本。
- 通過了哪些前置檢查。
- 讀取了哪些資料。
- 產生了哪些輸出。
- 在哪一個條件下停止。

### Traces：如何完成工作

Traces 用來了解 Agent 的處理路徑與工具調用軌跡。當結果不符合預期時，不能只知道最後失敗，還要知道 Agent 在哪一步採用了什麼輸入與判斷。

### Metrics：整體品質如何

Metrics 可用來評估：

- 升級判斷正確率。
- 差異覆蓋率。
- 阻擋條件是否被正確攔截。
- 執行效率與重跑成功率。

### Incomplete 機制

當資料不足或條件未滿足時，Incomplete 不代表系統失敗，而是代表系統沒有在證據不足時冒險產生答案。

### 分享心得

企業導入 AI 後，不能只看「有沒有成功產出」，還要看「能不能解釋產出」。可評估性是建立信任與持續改善的前提。

### 建議講述時間

約 3 分鐘。

## Slide 09｜五大可驗證原則

### 本頁目的

將前面的方法整理成可以實際採用的五項原則。

### 1. 垂直切片

每次先完成一個窄而完整的工作單位，而不是同時展開大量未驗證功能。

### 2. 完整追溯

所有產出都應該能回到輸入、規則、執行紀錄與證據，避免結果成為無法說明的黑盒子。

### 3. 隨時可恢復

狀態變更、輸出與執行紀錄都要透明。遇到問題時，可以回到上一個已知狀態，而不是只能重新猜測。

### 4. 不確定即停下

當遇到輸入不足、邊界條件、版本衝突或授權問題時，系統應該掛起並產出報告，等待人工判斷。

### 5. 無痛可接手

保持 Context 乾淨、精確與模組化，使下一位工程師或下一個 Agent 可以快速理解並接續工作。

### 分享心得

這五項原則可以變成每一個 AI 工程任務的啟動檢查表。若一個任務無法說明輸入、輸出、驗證與停止條件，就代表它還沒有準備好交給 Agent 自主執行。

### 建議講述時間

約 3–4 分鐘。

## Slide 10｜從快，到穩，再到可交付

### 本頁目的

總結 Vibe Coding 與 Agentic Engineering 的關係，並提出可帶回團隊的行動方向。

### 核心結論

Vibe Coding 提供前所未有的開發速度，讓我們更快得到第一個版本；Agentic Engineering 則補上企業交付所需要的工程控制：

- 可檢查：知道結果是否符合規格。
- 可治理：知道哪些動作需要限制與核准。
- 可追溯：知道輸出來自哪些輸入與執行過程。
- 可接手：讓其他人或 Agent 能夠理解並繼續工作。

### AI 與人的分工

AI 不應該取代人的業務判斷。更適合的分工是：

- AI 協助整理資料、執行比對、產生報告與發現差異。
- 人負責定義目標、判斷風險、核准高風險變更與承擔最終責任。

### 可帶回團隊的三個行動

1. 選擇一個低風險、但能端到端完成的工作流作為第一個垂直切片。
2. 先定義輸入、輸出、完成條件與阻擋狀態，再讓 Agent 開始實作。
3. 將測試、執行紀錄、報告與證據保留為下一次迭代可重用的工程資產。

### 結尾建議講稿

> AI 的價值不是代替人的判斷，而是讓每一次的判斷都更有證據。當我們把速度放進可驗證的流程，Vibe Coding 才能從個人效率工具，轉化為團隊可持續的交付能力。

### 建議講述時間

約 2–3 分鐘，最後保留 Q&A 時間。

## 三、整場分享的一句話總結

> Vibe Coding 讓我們更快做出東西；Agentic Engineering 讓我們知道做出的東西為什麼可信、如何驗證、如何治理，以及如何交給下一個人接手。
